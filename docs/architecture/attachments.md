# Attachments

Images go to Ollama images, everything else becomes text on the message row.

Two kinds, two destinations, both persisted on the message row. Images go into Ollama's `images` field as base64 (vision models only). Everything else is read in the renderer (`src/lib/attachments.js`), stored as `files: [{name, content}]`, and appended to that message's `content` by `getApiMessages` — Ollama has no file channel, so the extracted text **is** the attachment, and a picker never exposes a path, so the text is the only copy that exists. `getApiMessages({ files: false })` is what the side-chat context transcript and the follow-up call use: a 100 KB attachment would swamp the 4000-char transcript they are actually summarising. Caps are per file (100 KB) and per message (200 KB), applied at pick time in `InputArea`; types are matched by **extension**, not MIME, because source files have no registered type (`file.type` is empty for `.rs`/`.go`/`.py`). The `accept` attribute is generated from the same lists as the filter (a wildcard would offer SVG and HEIC, which Ollama cannot decode), and a rejected pick is reported in a `role="alert"` notice rather than dropped silently.
